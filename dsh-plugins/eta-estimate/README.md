# 任务剩余时间预估 (DSH plugin) · v2.0.0

DeepSeek Harness Web UI 插件。任务运行期间在输入框下方显示一枚胶囊。

## 安装

```
github:x-ww/kit#path:dsh-plugins/eta-estimate
```

在 Web 界面「插件 → 添加插件」把上面这串直接粘进输入框即可，不需要克隆仓库。
更新后重新安装一次并刷新页面。

## 为什么 v1 几乎不可用

v1.2.0 的做法是：按「已完成步数」查一张实测表得到「剩余步数」的分位数，再乘一个
**固定的 6.4 秒/步**。回测声称中位误差 79%。实际用起来误差远大于此，原因有四：

1. **步数计数器是死代码。** `props.useChat(s => s.partial)` 读错了键——Chat 快照里没有
   顶层 `partial`，它在 `s.legacy.partial`。所以 `partial.step - 1` 分支从未执行，步数
   只能靠「已定稿 assistant 节点数」兜底，与日志里的 `step/end` 定义不一致（最多差 1，
   且在工具执行窗口里长时间滞后）。
2. **完全忽略已用时。** 不管任务跑了 10 秒还是 20 分钟，`STEP_PRIOR` 给出的剩余步数中位数
   始终在 16–20 步附近，于是胶囊几乎一直显示「≈ 2 分钟」。这不是倒计时，是一个常数。
3. **固定步速已过期。** 6.4 秒/步来自旧模型的日志；换模型、换任务类型后完全不准。
4. **对短任务系统性高估。** 时长低于 1 分钟的任务占了近 40%，v1 给它们一律报「≈ 2 分钟」，
   中位偏差达到 17 倍。

## 实测对比

数据：本机 `session.v4.jsonl.zstd` 日志，**98 个会话 / 251 个已完成轮次 / 1757 个采样点**。
采样点是每轮耗时的 10%…90%（**按墙钟时间，不是按步数边界**），因此特征与插件运行时任意时刻
能观测到的状态一致；`steps` 按日志定义取 `step/end` 已结束的步数。
评估用 **5 折按会话分组交叉验证**（测试会话的任何轮次都不参与训练）。

| 模型 | 中位相对误差 | 中位偏差 (预测/真实) | 80% 区间覆盖率 | 中位绝对误差 |
|---|---|---|---|---|
| v1.2 固定 6.4s/步 + 步数表 | **194%** | 2.94× | 40% | 103 秒 |
| v2 已用时 + 步数对数模型 | **81%** | 0.99× | 77% | 32 秒 |

分长度看，修复最明显的是短任务：

| 轮次时长 | v1.2 中位误差 | v2 中位误差 | v1.2 覆盖率 | v2 覆盖率 |
|---|---|---|---|---|
| < 1 分钟 | 1636% | 82% | 7% | 74% |
| 1–10 分钟 | 67% | 77% | 70% | 79% |
| > 10 分钟 | 77% | 76% | 34% | 76% |

复现：`python3 backtest.py`（需要 `zstd` 命令行工具；可用 `DSH_SESSIONS_DIR` 指定日志目录）。

## 结论：默认不再常驻显示预测数字

轮次耗时跨度是 **0.3 秒到 73 分钟（约 4 个数量级）**。即使修好 bug、换掉模型，
点预测的中位误差仍有约 81%，80% 区间宽达约 30 倍。把它常驻显示成一个数字会继续误导人。

所以 v2 把**默认显示改成确定性的事实**（误差为 0）：

- 有任务计划时（agent 用了 `todo_write`）：`任务 3/7 · 已用时 2 分钟`
- 没有计划时：`已用时 2 分钟 · 第 12 步`
- tooltip：`本次已用时超过 60% 的历史任务`、样本数、以及免责说明

**点击胶囊**可切换到「时间预估」模式，显示经过校准的 80% 区间 `预计剩余 ≈ X–Y`；
再点一次切回。选择存进 `localStorage`，跨刷新保留。

## 模型

```
log(剩余秒数) = 0.281552
              + 1.000945 * log(已用时秒数 + 1)
              - 0.269862 * log(已完成步数 + 1)

区间 = exp(fit + q10 / q50 / q90)
q10 = -1.727042   q50 = -0.022416   q90 = 1.780031
```

只用两个运行时量：`elapsed`（来自 `legacy.turnTimings.startTime`，epoch 毫秒）和
`stepsDone`（来自 `s.timeline.turns.get(turn).steps` 中 `status === 'closed'` 的数量）。
不依赖固定步速，因此换模型后不会像 v1 那样整体漂移。

历史耗时分位数（秒，用于 tooltip 的「超过 X% 的历史任务」）：
0.3 / 1.1 / 5.3 / 21.1 / 37.2 / 60.6 / 90.8 / 178.8 / 306.3 / 422.2 / 733.2 / 1229.6 / 4399.4。

## 已知限制

- 剩余时间**原理上高度不可预测**；v2 把误差砍掉一半以上，但仍不是可靠的倒计时。
  这就是为什么默认模式只报事实。
- 80% 校准区间很宽（约 30 倍跨度）。这是诚实的代价，不是精度。
- `todos` 是整会话快照（最近一次 `todo_write`），若列表里混有很久以前完成的条目，
  done/total 会失真；此时它只作为进度参考，不参与时间计算。
- 模型来自本机历史；任务类型或模型分布大幅变化后应重新跑 `backtest.py` 拟合。
- 插件只读 Client 投影与 `localStorage`，不写会话事件、不读其他插件 DOM。
- 支持 8 种语言；样式仅引用 DSH 主题令牌。

## 文件

- `index.js` — Host 半（空实现）
- `client.js` — 客户端模块：字典、模型、进度读取与胶囊渲染
- `backtest.py` — 回测与拟合脚本，可复现上面所有数字
- `cordis.patch.yml` — 插入插件行
- `locale/*.json` — 插件管理页显示元数据
- `icon.svg` — 原创计时器图标
